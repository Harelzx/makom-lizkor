# נוהל תפעול - מקום לזכור

עודכן ב־14.10.2026. אחראי: הראל ארונוביץ׳. הגרסה הפעילה וראיות השחרור נקבעות ב־[רשומת ההמשך](agent-handoff.md), לא משם תיקיית build. אין קישורי מעקב, סודות, כתובות או תוכן פניות ביומן אירוע או ב־Git.

## בדיקה שוטפת והתראות

- GitHub availability: שבע GET ללא סודות/עוגיות, פעם בשש שעות UTC בדקה23, וגם הפעלה ידנית; HTML/CSP, version/feed וארבעה נתיבים פרטיים. publication handoff אחד מותר; אין retry לשגיאת שרת או כתיבה. job עד שתי דקות, בלי npm ci. תזמון GitHub עשוי להתעכב; אינו SLA או זיהוי מיידי. ארבע הרצות ביום, דקות וחיוב לפי התוכנית והמשך בפועל, ללא הרחבת תקציב.
- כשל Actions מופיע ב־GitHub. ב־13.10 הראל סיפק אישור הגעה של שתי הודעות כשל מ־notifications@github.com לריצות38366388002 ו־38367294893; ערוץ זה אינו תלוי בדואר האתר. יש לוודא שההגדרות נשארות פעילות. זמינות הבדיקה עצמה אומתה בהרצה ידנית38366895185; אירוע מתוזמן עדיין לא נצפה.
- Cloudflare: שתי התראות10USD קיימות נשמרו; אלה התראות ולא hard cap. test של מדיניות התקציב הקיימת התקבל200 והראל אישר קבלה בתיבה ב־13.10. usage מפורט נחסם בהרשאות הנוכחיות, שלא הורחבו.
- runtime issues: מדיניות ההתראה (Workers Observability, «Makom Lizkor runtime issues», למייל המפעיל) קיימת, אבל **זיהוי ה־Issues ב־Worker כבוי** (נבדק ב־22.10 בלוח: «Enable issue detection»). פריסה של Wrangler בלי `observability.issues.enabled` מכבה אותו, ולכן ההתראה מעולם לא נשלחה. ההפעלה אינה רק שורת תצורה: Issues שומר פרטי בקשה לכל מופע וסופר גם שורות `console.error` שלנו, וזה סותר את `invocation_logs: false` ואת מה שמדיניות הפרטיות מבטיחה על היומנים; זו החלטה של הראל. בינתיים: קריסה מלאה מכשילה את בדיקת הזמינות של GitHub; חריגה מזדמנת ממגבלת CPU או זיכרון (1102) בבקשה בודדת או ב־cron אינה מתריעה.
- מוני /api/ops ומסך המנהל פרטיים ומדוגמים. לוג חדש mail_delivery_failed שומר רק outcome קבוע; mail_budget_unavailable מציין חסם מסד. אין provider error, גוף או capability בלוג. מכסה צפויה אינה runtime error; גם מטא־דאטה אינו אישור להגעת מייל.
- תקציב המייל הציבורי (230 ביום): מיילים שפעולה של מבקר שולחת (אימות, קישור מעקב, טופס יצירת קשר) לא יכולים לקחת את 30 האחרונים (`VISITOR_RESERVE`). הם שמורים להתראות למנהלים על בקשות הסרה ולהחלטות. כתובת אחת מקבלת מיילי אימות לשלוש הצעות לכל היותר ביממה (`VERIFY_PER_ADDRESS_DAY`), והשאר ממתינות ליום הבא.
- security.yml: audit וסריקת סודות שבועית; compatibility.yml: בדיקת דפדפנים שבועית. אינם מבחן חדירה חיצוני.

## טיפול באירוע

1. רשום UTC, גרסה/ריצה, סוג והיקף ידוע/לא ידוע; בדוק endpoint חי ומצב ספק רשמי. אין הסקת תקיעה מתאריך בלבד.
2. בחשד לחשיפה, בעל המערכת מחליט על עצירת כתיבה/פרסום דרך ההגנה הקיימת, שומר Access snapshot ומבודד את הנתיב. לא פותחים wildcard או מורידים אימות כדי לבדוק.
3. שמור לוג קודים מוגבל וראיות; בלי MIME, סוד, גוף פנייה או קישור. בדיקת תיבה מוגבלת להודעה הנחוצה והמותרת.
4. Gmail: בדוק OAuth, stopped/uncertain והגעה למכסה ב־ops. אין resend לא ודאי, fallback relay או העלאת gmail.modify לאתר. פנייה שנכשלה אינה מבטיחה מסירה; אימות פועל במסלול הניסיונות הבטוחים הקיים.
5. סוד שנחשף מבוטל/מוחלף בידי בעל המערכת; אין scope חדש או מחיקת ראיות. מעריכים אם לבטל יכולות מעקב שנפגעו.
6. המפעיל מעריך דיווח לרשות/נפגעים לפי הדין והאירוע, בעזרת גורם מתאים. לא שולחים בשמו הודעות לצד שלישי ללא אישור. מיישמים תיקון ובדיקה ממוקדת לפני חזרה.

## rollback ושחרור

**עדכון האתר החי בפקודה אחת** (מ־21.10.2026; מחליף את ערכות השחרור הידניות): מהמחשב של הבעלים, אחרי מיזוג ל־main.

- `npm run release -- --dry-run`: הכול עד הפריסה, בלי לגעת באתר החי. כדאי להריץ קודם.
- `npm run release`: משחרר את הראש של main. הסקריפט (`scripts/release/release.mjs`) מחכה לריצת ה־CI של אותו commit (החבילה המלאה, כולל הדפדפנים, WebKit והכיסוי, לא מדולגים) ולפריסה שלו ל־staging. אחר כך הוא בונה את אותו commit ב־worktree נקי עם ה־sitekey האמיתי, ואורז. את התצורה הוא משווה לחבילה שרצה עכשיו בפרוד (לפי ה־tag החי), ועוצר על כל שינוי שלא צוין ב־`--accept-drift=vars.X,...`. הוא מריץ את חוסמי השחרור, קורא את Access ואת הגרסה החיה, פורס פעם אחת, ובודק אחר כך את הגרסה, את המיגרציות, את Access ואת האתר החי.
- **מיגרציות: רק expand-only.** אסור למחוק, לשנות שם, להוסיף trigger או אינדקס ייחודי, או להוסיף עמודת חובה בלי ברירת מחדל, ואסור לערוך מיגרציה שכבר שוחררה. `scripts/migration-check.mjs` אוכף את זה בכל בקשת מיזוג (בשלב `static` של ה־CI), והסקריפט אוכף אותו שוב מול הגרסה החיה לפני הפריסה. מיגרציה ממתינה מוחלת רק עם `--apply-migrations`, אחרי תמונות ה־before ורגע לפני הפריסה. שינוי שחייב לצמצם את הסכמה מתבצע בשני שחרורים: באחד מפסיקים להשתמש בעמודה או בטבלה, ובשחרור מאוחר יותר מסירים אותה, בהחלטת הבעלים.
- הראיות נשמרות ב־`../agent-evidence/release-<sha7>-<תאריך>/`. הסודות והלוג הגולמי נשמרים ב־`../.production-private/` (שם גם `release.json` עם מזהה החשבון).
- אם GitHub איבד את אירוע המיזוג (תקלה אצלו, כמו ב־21.10.2026) ולא התחילה ריצת `ci` על הראש של main, הסקריפט מחכה 90 דקות ועוצר בלי לפרוס. ריצה כזו לא תתחיל מעצמה ואין לה הפעלה ידנית: ממזגים את השינוי הבא (גם קטן), והמיזוג שלו מפעיל את הבדיקות על כל מה שנצבר. לא דוחפים ישירות ל־main בשביל זה.
- `npm run release:rollback`: מחזיר את הפרוד לגרסה שרצה לפני השחרור האחרון, ובודק שהאתר עונה כמותה. קוד בלבד: לא נתונים, לא מיגרציות, לא Access. **עוד לא הופעל על הפרוד.**

מפרידים תקלת קוד מתקלה בנתונים/ספק. לא משחזרים מסד עבור באג UI. ב־Cloudflare Versions בוחרים גרסה קודמת רק לאחר התאמת source/receipt, bindings/secrets והתאמה למיגרציות. rollback קוד אינו rollback נתונים ואינו ביטול הסרות.

שינוי חדש דורש בדיקות ממוקדות, CI full וכיסוי ראשון מדויק, staging אוטומטי באותוSHA עם תשע pass וחבילת production מול ענן/Access טריים. אין סודות בבנייה או deploy עוקףCI. רשומת deploy כוללת hash קבצים, SHA, CI/staging, version/tag, הגרסה הקודמת וקריאת תוצאה חיה.

אחרי פריסה: version, פיד רענן, גבולות פרטיים, תמונה/OG, טופס נגיש ומנהל. שינוי דואר דורש הודעת בדיקה אחת ליעד הפרויקט והגעה נצפית. הוספה/אישור/משיכה נבדקות בדמה עם הצהרות ואישור מחיקה ממוקד; לא בנתוני אדם אמיתי. אין חזרה על תרגילי שחזור שכבר נסגרו כשמחזור החיים לא השתנה.

## בקשת עיון, תיקון או מחיקה

בקשה מגיעה בטופס ההסרה, במייל או בטופס "כתבו לנו". משיבים תוך 30 יום (תקנות הגנת הפרטיות, עיון); סירוב מנומק נשלח תוך 21 יום. רושמים ביומן הפניות מועד, מבקש, מה התבקש ומה נעשה, בלי להעתיק את תוכן הבקשה ל־Git.

1. מזהים את המבקש לפני שמוסרים מידע: משיבים רק לכתובת שממנה נשלחה ההצעה או הבקשה, או מבקשים פרט שרק הוא יודע.
2. עיון: מוצאים לפי מזהה המקום (קישור השיתוף) בלוח הניהול, ולפי המייל בתיבת המיזם. לא מוסרים פרטים של אדם אחר.
3. מחיקת מקום שלם: בלוח הניהול, "חיפוש מקום", הדבקת קישור השיתוף, "חיפוש המקום", "מחיקת המקום לצמיתות". המחיקה סופית: התוכן, התמונות, המקורות ופרטי השולח נמחקים מיד, והיא נרשמת ב־ledger כהסרה, כך ששחזור מגיבוי לא מחזיר אותם. מהגיבויים עצמם הם נעלמים תוך 37 יום.
4. הסתרה בלבד (פרט אחד, או עד בירור): "הסתרת מה שסומן" באותו מקום; "החזרה לאתר" רק עם סיבה כתובה.
5. מחיקת פרטי מבקש הסרה ונוסח בקשתו: בכרטיס הבקשה, "הסתרה ידנית ומחיקה", "מחיקת פרטי המבקש". הבקשה נסגרת ונשאר רק שהייתה ואיך טופלה.
6. מייל בתיבת המיזם: מוחקים את השרשור ב־Gmail ומרוקנים אותו מהאשפה, אם הבקשה כוללת אותו.
7. משיבים למבקש מה נעשה ומתי, ומתעדים.

שולח שהוסיף מקום יכול למשוך אותו בעצמו מקישור המעקב; זו מחיקה מלאה, כמו בסעיף 3.

## גיבוי ומפתחות

export מוצפן, ledger וסינון שחזור ל־DRILL_DB נפרד אומתו תפעולית ב־11.10. קצב קיים: תחזוקה15 דקות, export23h, drill שבועי. snapshot ידני תחום אינו מאפס cadence. לא מוחקים רשומות הצלחה ולא משניםcreated_at/ceiling/guards כדי לכפות בדיקה.

לפני שחזור: export המוצלח האחרון ונקודת המחיקה האחרונה; רק החדש ביותר והטרי במסגרת החסם. סינון תפוגה/ledger קודם לכתיבה לתרגול, שמירת מועדים ובדיקת suppression לפני חזרה. מנקים תרגול לפי התהליך המאושר. Time Travel מוקדם אינו תחליף. אובדן עדכונים מאז הגיבוי נרשם.

מפתח בעלים אינו עולה לענן. עותק מוגן נמצא מחוץ למחשב, ב־Apple Passwords עם סנכרון iCloud; הראל אישר ב־14.10 שהוא נפתח באייפון. קודי MFA נשמרים בידי המפעיל, לא בצ׳אט. נעילת R2 אינה הוכחת שחזור בלי המפתח או מחיקה פיזית.

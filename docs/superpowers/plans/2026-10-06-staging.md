# Staging: הכנה, בדיקות בענן, ומה שנדרש מ־Harel

**המטרה:** חשבון staging נפרד, נתונים סינתטיים בלבד, על `workers.dev` מאחורי Cloudflare Access. כל commit ב־`main` שעבר CI נפרס אליו ונבדק שם. ‏`release.yml` דורש ריצת staging מוצלחת על ה־commit שהוא משחרר.

**הרשאה (Harel, ‏2026-10-06):**

- **מאושר:**
  - חיבור המאגר הפרטי;
  - דחיפה של `main` שנסקר;
  - הכנה מקומית של ה־staging;
  - גילוי read-only של Cloudflare.
- **לא מאושר:**
  - רכישות ושימוש בתשלום;
  - פריסה לייצור;
  - שינוי בענן בלי בקשה קונקרטית.

**Spec:** ‏14.1 (סביבות), ‏14.2 (שחרור), ‏12.2 (הרשאות; תוקן ל־GitHub Free), ‏13 (בדיקות על קצה אמיתי).

## מה מוכן (commit `91df608`)

- **`wrangler.jsonc` → `env.staging`:**
  - Worker בשם `makom-lizkor-staging`;
  - D1 בשם `makom-staging` (ה־id נקבע אחרי היצירה) ושלושה buckets ב־`eu`;
  - `ENVIRONMENT=staging`;
  - אותם bindings, rate limits ו־vars כמו בייצור.

  הייצור לא השתנה.

- **`scripts/staging-check.mjs`:**
  - בודק שה־staging לעולם אינו development: `/__dev` ו־`X-Test-Now` סגורים;
  - בודק שהוא לא חולק דבר שמחזיק נתונים עם הייצור;
  - ב־`--deploy` דורש את ה־id האמיתי ואת ערכי החשבון.
- **`.github/workflows/staging.yml`:** אחרי CI מוצלח על push ל־`main`, הוא עובר על אותו commit לפי הסדר:
  1. בדיקת ההגדרות;
  2. build עם `CLOUDFLARE_ENV=staging`;
  3. מיגרציות;
  4. deploy מתויג ב־commit, עם secrets דרך `--secrets-file`;
  5. `edge-check` דרך Access, עם service token.
- **`ci.yml`:** ריצה אחת לכל commit (ב־`main` וב־PR).
- **`ci-policy`:**
  - secrets מסוג `STAGING_*` רק ב־`staging.yml`, ושמות של secrets ייצור רק ב־release ו־rollback;
  - deploy מחוץ לשניהם רק עם `CLOUDFLARE_ENV=staging`.

## בדיקות בענן, לפי הסדר

כל שלב נרשם עם ה־commit שנפרס, ומופרד בין תוצאה מהענן, תוצאה מקומית ובדיקה שדולגה.

1. **בסיס:**
   - הדף נטען;
   - הכותרות ו־`private, no-store` (‏`edge-check`);
   - `/__dev` ו־`X-Test-Now` לא קיימים;
   - `workers.dev` מאחורי Access.
2. **הזרימה:** הגשה עם Turnstile אמיתי, אישור מודרטור, ופיד.
   - **מודרטור אוטומטי:** service token לעולם אינו מודרטור (‏spec 12.1). לבדיקה אוטומטית של אישור צריך אחת משתיים:
     - **(א)** כתובת מייל סינתטית למודרטור staging, שנכנסת דרך Access ב־one-time PIN. האישור ידני.
     - **(ב)** רשימת service tokens שמותר להם לאשר, רק כש־`ENVIRONMENT=staging`, עם בדיקה שבייצור זה סגור. דורש החלטה של Harel ובדיקה של סשן הפרטיות.
   - **ההצעה:** (ב), בגלל שהנתונים סינתטיים. עד ההחלטה, השלב הזה ידני.
3. **תמונות, דפי שיתוף ותמונות שיתוף:** תמונת שיתוף לכל מקום דורשת Workers Paid (זמן CPU של הרינדור).
4. **בכותרות ובקצה:**
   - כניסה אמיתית ב־Access;
   - cache בקצה: `no-store` לדפדפן, ו־`max-age` בקצה;
   - הסתרה ו־purge לפי `Cache-Tag`, ומדידה של הזמן עד תוכן טרי.
5. **עבודות מתוזמנות וגיבוי ושחזור סינתטי:**
   - ה־cron;
   - הייצוא המוצפן למפתח סינתטי;
   - התרגיל;
   - מסלולי A ו־B על D1 נפרד.
6. **עומס מוגבל** (`tests/load/oct7.js`), רק אחרי שהזרימות הבסיסיות עובדות.

## מה נדרש מ־Harel (בקשה אחת)

ראו את הסיכום בשיחה ואת `docs/agent-handoff.md`. ההחלטות הן:

- זיהוי חשבון ה־staging;
- הפעלת R2;
- Workers Paid או Free;
- token מוגבל לחשבון;
- אפליקציית Access ו־service token;
- Turnstile widget;
- ה־secrets וה־variables במאגר;
- מסלול השחרור לייצור ב־Free;
- ההחלטה על מודרטור אוטומטי (2ב).
